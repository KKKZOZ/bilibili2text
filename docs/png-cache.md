# PNG 导出缓存

预生成与按需导出的 PNG 都保存到 `cache/png/<唯一 ID>/<文件名>`，对象存储会加上
配置的 `base_prefix`（默认路径为 `b2t/cache/png/`）。本地存储使用输出目录下的
`cache/png/`，不依赖渲染临时目录。

## 对象存储负责过期

MinIO/R2 的对象生命周期规则负责在上传后 14 天清理该前缀。生命周期删除是异步的，
不保证在第 14 天的精确时刻删除。后端没有 PNG 定时扫描或删除线程；对象仍存在时
可以继续使用，对象存储实际删除后才视为缓存失效。读取和下载不续期。

配置当前 MinIO/S3（包括 R2）的规则，保留桶内其他生命周期规则：

```bash
uv run python -m scripts.configure_png_lifecycle
uv run python -m scripts.configure_png_lifecycle --apply
```

规则只匹配 PNG 缓存前缀，不影响源 Markdown、HTML、转写和 PDF。本地文件存储不具备
对象生命周期，需要自行定期清理该目录，后端同样会处理文件缺失。

## 按需检查和重新生成

SQLite 的 `png_cache` 表记录源文件、变体、渲染模式、版本和生成时间。每次请求导出：

1. 查找对应缓存；不同模式独立，预生成只对应默认模式。
2. 缓存对象仍存在则复用，不以数据库时间推断它已经被删除。
3. 收到 `NoSuchKey` 等对象不存在结果后，移除失效缓存索引和历史 PNG 记录，再重新生成。
4. 鉴权错误、桶不存在、网络故障等正常报错，不会触发无意义的重新生成。

旧的直接下载链接若指向已经删除的对象，返回 410 和重新导出提示；重新点击源文件
的导出操作会生成新链接。没有再次访问的失效索引可能保留在数据库中，不占用对象
存储空间；目前没有定时数据库清扫。

修改渲染配置时更新 `b2t/png_cache.py` 中的 `RENDER_VERSION`，避免复用旧参数图片。

## 迁移历史图片

```bash
uv run python -m scripts.migrate_png_cache
uv run python -m scripts.migrate_png_cache --apply
```

这是一次性管理操作：按旧对象时间清理已超过 14 天的 PNG，校验并迁移其他图片，更新
历史索引。旧图片标记为旧渲染版本，不作为新参数的缓存命中。迁移期间应停止旧版本
写入。复制到新位置后，对象存储生命周期会从复制时间重新计时。

迁往 R2 时必须重新设置目标桶的生命周期规则；源桶规则不会随文件复制。缓存索引仍
随本地历史数据库保留，后续数据库迁移时也应包含该表。
